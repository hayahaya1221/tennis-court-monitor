# 竹早・錦糸公園テニスコート夜間空き監視（試作版）

## 現状と確認範囲

2026-11-17に、ログインせず両施設の公開予約画面で施設選択→日付別表示→時間帯別表示まで実際に操作した。

- 竹早：平日／土日祝の両施設カテゴリを選ぶと第1～5コートが表示された。時間帯画面ではA～Fの区分ごとの `vacant` / `full` 等を識別でき、F区分を個別判定できた。
- 錦糸公園：屋外スポーツ施設→公園運動場→Ａ～Ｄ面。日付別カレンダーで複数面を選択すると、時間帯画面に面ごとの13個（8:00～21:00）の時間枠が表示された。
- 両サイトの月間表示は動的に更新される。日付別の「一部空き」自体を予約可能とは扱わない。
- 月間表示の操作時にサイト側のCloudflare Turnstile認証処理が入る。**このプログラムは認証処理を直接呼び出したり、保護を回避したりしない。** 通常のブラウザUI操作に失敗した場合は、その施設を取得失敗にする。

**重要：** ブラウザ上の手動調査と判定ロジックのユニットテストは完了しているが、このコードによる予約サイトの完全巡回は未検証。実行環境のChromium起動が権限制限で失敗したため、実際のスケジュール監視が成功するという保証はない。GitHub Actionsなどに配置後、手動実行（`workflow_dispatch`）で検証が必要。

## 判定条件

| 施設 | 対象 | 通知 |
|---|---|---|
| 竹早 | 全曜日、今後2か月以内、1～5番コート | F区分（18:00～21:00）の**先着予約可能**な状態のみ |
| 錦糸公園 | 全曜日、今後2か月以内、Ａ～Ｄ面 | 18–20、19–21の連続2時間（別面でも可）、または19–20、20–21の単独1時間 |

錦糸公園の18–19単独枠は通知しない。連続2時間に含まれる1時間の通知は省略する。

## ファイル

- `src/sites.mjs`：ブラウザUIを操作し、候補日と時間帯別空きを取得
- `src/slots.mjs`：2施設の通知条件、日付、重複排除、通知文を判定
- `src/monitor.mjs`：巡回、通知、取得失敗、状態ファイル保存
- `test/slots.test.mjs`：判定のユニットテスト
- `state/seen.json`：前回通知済みの枠を記録する状態ファイル
- `.github/workflows/tennis-monitor.yml`：日本時間を問わず毎時50分頃に起動するGitHub Actions例

## ローカル実行

```bash
npm install
npx playwright install chromium
npm test
npm run check
```

環境変数：

| 変数 | 用途 |
|---|---|
| `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` | 2つとも設定された場合のみTelegramへ通知 |
| `STATE_PATH` | 前回記録の保存先。初期値 `./state/seen.json` |
| `BETWEEN_DAY_REQUESTS_MS` | 候補日を開く間隔。初期値800ミリ秒 |
| `CHROMIUM_EXECUTABLE_PATH` | Chromiumの実行ファイル指定（任意） |
| `PLAYWRIGHT_CDP_URL` | 管理されたリモートブラウザ接続先（任意） |

Telegram設定なしで実行すると結果はコンソールへ表示されるが、通知済みには記録しない。**ユーザーへのプッシュ通知が必要な場合はTelegramの設定が必要。** 未確認の日付、抽選、申込期間外などは通知しない。

## 1時間ごとの自動実行（GitHub Actions例）

1. GitHubリポジトリの**ルート直下**に、このフォルダの中身を配置する。
2. リポジトリの「Settings → Secrets and variables → Actions」に `TELEGRAM_BOT_TOKEN` と `TELEGRAM_CHAT_ID` を登録する（値をソースに書かない）。
3. 「Actions → Tennis court availability → Run workflow」で**手動テスト**を実行し、両施設について `status: ok` と日付確認件数が出ることを確認する。
4. 問題がなければ、cron `50 * * * *` の毎時実行を有効にする。GitHub Actionsは混雑時に実行が遅延したり、スケジュールされた実行が失われたりする場合がある。
5. `state/seen.json` をworkflowがcommit/pushするので、default branchのworkflow書込権限を許可する。ブランチ保護がある場合は別の永続保存先が必要。

**この手順を行う前に通知先とGitHubリポジトリが必要。** 現時点では外部への配置や有効化は行っていない。既存ChatGPT定期タスクは別物であり、このコードを保存しただけでその定期タスクが動くわけではない。

## 安全性・限界

- ログイン・予約・ユーザーデータ入力はしない。
- CAPTCHAやTurnstileの回避はしない。認証でブロックされた場合は取得失敗を表示する。
- 取得が完了しないサイトは「空きなし」にせず、以前通知済みの状態も削除しない。
- 同じ取得エラーは通知先への連絡を1日1回までに抑える設計（状態保存が機能する場合）。
- 空き枠は表示の直後に埋まることがある。通知は予約の確約ではない。
- 定期アクセスはサイトの利用規約・アクセス負荷に配慮して実行する。過度なアクセスになる場合は間隔や対象を減らす。
- 取得候補日が多い場合はページ遷移回数が増えるため、初回試験では所要時間とサイト応答を確認する。特にGitHub Actionsの45分タイムアウトに注意。
